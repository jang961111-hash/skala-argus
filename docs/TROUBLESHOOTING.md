## 1. 하루 1,001번째 요청부터 작업요청 등록이 전부 500

- **상황**: 2026-09-28 재측정 중 요청번호(`WR-YYYYMMDD-NNN`) 채번에 동시성 부하를 걸다가 발견했다. 당일 누적 요청이 1,000건을 넘도록 750건을 추가 등록하자 일부가 500으로 실패했다.
- **영향**: 750건 중 **201 ×718, 500 ×32**. 서버 로그는 `UNIQUE constraint failed: work_requests.request_no`. 당일 요청이 1,000건을 넘는 순간부터는 등록이 계속 실패하는 구조다. 실제 업무량으로 하루 1,000건은 드물다는 점도 함께 적어 둔다.
- **가설**:
  1. 동시 요청끼리 같은 번호를 읽는 경합 — 부하 테스트 중에 나왔기 때문에 먼저 떠오르는 원인이다.
  2. 다음 번호를 계산하는 로직 자체가 틀렸다.
- **검증**:
  - 가설 1 기각: 같은 동시성(10·50)으로 100건씩 넣은 측정은 SQLite·PostgreSQL 모두 **중복 0, 500 0**이었다. 실패는 당일 누적 1,000건을 넘긴 뒤에만 났다.
  - 가설 2 확인: 응답에 나온 요청번호의 최솟값이 `WR-20260928-1000`, 최댓값이 `WR-20260928-999`였다. 문자열 정렬이 뒤집혀 있다는 뜻이다.
- **원인**: `backend/app/repositories/request_no.py`가 당일 최대 번호를 `func.max(request_no)`로 구한다. 이건 **문자열 비교**라 `"…-999" > "…-1000"`이 된다. 그래서 다음 번호를 계속 `1000`으로 계산해 이미 있는 번호를 다시 발급했고, UNIQUE 충돌 재시도 5회를 모두 써 버린 뒤 500이 났다. 기존 테스트는 3건만 만들었고 번호 형식 정규식도 `\d{3}`으로 고정돼 있어서, 세 자리를 넘는 경우가 설계에서 빠져 있었다.
- **해결**: 최댓값을 "길이 내림차순 → 문자열 내림차순"으로 정렬해 구하도록 바꿨다. 숫자 순서와 같아지고, SQLite와 PostgreSQL에서 같은 SQL로 동작한다. 커밋 `bfd716b` (브랜치 `fix/request-no-over-999`) → **PR #1** https://github.com/jang961111-hash/skala-argus/pull/1 (머지 전)
- **결과**: 999·1000을 미리 넣고 다음 번호가 1001인지 보는 회귀 테스트를 먼저 작성해 **수정 전 실패(UNIQUE 위반)**를 확인했고, 수정 후 통과했다. 전체 pytest 30 → **31 passed**.
- **재발 방지**: 경계 회귀 테스트(999 → 1000 → 1001) 추가, 번호 형식 정규식을 3자리 이상으로 완화.
- **남은 것**: 목록 API의 `sort=requestNo`도 문자열 정렬이라 1000번 이후가 999 앞에 표시된다(PR #1 리뷰에서 LOW로 지적, 미수정). 재시도 경로(`request_no.py`의 IntegrityError 분기)는 여전히 테스트가 실행하지 않는다(커버리지 미실행 행).
- **배운 점**: 문자열로 저장한 숫자는 정렬·비교에서 반드시 자릿수 경계(9→10, 99→100, 999→1000)를 테스트한다.

## 2. E2E 검사가 실패해야 할 때 조용히 PASS (원본 I-12, I-09)

- **상황**: 2026-09-03, 라이브 E2E(`scripts/e2e_live_v3.sh`) 출력에 `PASS … FAIL:['aiRunning','draft','pending','rejected']`라는 모순된 줄이 찍혔다. 판정은 PASS인데 값에는 FAIL 문자열이 있었다.
- **영향**: 값에 공백이 생기는 건 주로 실패 경로다(예: `FAIL:['a', 'b']`). 즉 **검사가 실패해야 할 때 통과로 셀 수 있는 구조**였다. 통과 개수만 보면 알 수 없다. 같은 패턴을 쓰는 검사가 10곳이었다.
- **가설**:
  1. 출력 모양만 이상한 표시 문제다 — 처음엔 이렇게 보였다.
  2. `python -c` 안의 집합 리터럴 `{'draft',…}`을 bash가 brace expansion으로 펼쳤다 (당시 첫 가설, I-12에 기록).
  3. 여러 줄 명령치환 결과를 `chk` 인자로 바로 넘겨서 공백 기준 단어 분리가 일어났다.
- **검증**: 인자를 찍어 보는 디버그 계측으로 `chk`가 인자 3개가 아니라 **`argc=6`**을 받는 것을 확인했다. 같은 응답 본문에 해당 파이썬 스니펫을 단독으로 돌리면 `OK`가 나왔다 → 백엔드 응답은 정상이고 **검사 쪽이 틀렸다**. 가설 1은 기각했다. 인자가 쪼개지는 근본 원인은 가설 3의 단어 분리로 정리됐다.
- **원인**: 아래처럼 명령치환을 인자 자리에 바로 쓰면, 출력에 공백이 있을 때 인자가 여러 개로 쪼개진다. 그러면 `[ "$2" = "$3" ]`가 엉뚱한 조각끼리 비교한다.
  ```bash
  chk "이름" "$("$PY" -c "
  ...python...
  ")" "OK"
  ```
- **해결**: 명령치환을 먼저 변수에 대입하고(`_cv1=$(…)`, 대입 문맥에서는 단어 분리가 없다) `"$_cv1"`로 넘기도록 10곳을 모두 바꿨다. 현재 `scripts/e2e_live_v3.sh`의 `_cv1`~`_cv10`이 그 결과다. 수정은 스크립트가 처음 커밋된 `745683c`에 들어 있다(수정 전 버전은 커밋되지 않았다. 커밋 메시지에 경위를 적어 두었다).
- **결과**: 수정 후 해당 대시보드 검사가 `OK`로 제대로 판정되고 전체 **72 통과 / 0 실패**. 2026-09-28 재측정에서도 3회 연속 72/0.
- **재발 방지**: 값 비교 검사는 반드시 변수에 먼저 담아 넘긴다. 당시 로그의 I-12는 "미해결"로 남아 있는데, 실제로는 이 수정으로 해결됐다(원본 로그의 정합성 메모에 기록).
- **배운 점**: 통과 개수는 검사가 실제로 비교하고 있다는 증거가 아니다. "통과인데 값이 이상한" 줄은 인자부터 찍어 본다.

## 3. E2E를 연속으로 돌리면 이전 서버에 붙어 대량 실패 (원본 I-06 → I-07)

- **상황**: 2026-09-03 15:55, 증거 수집 스크립트로 돌린 E2E가 **27/64**로 떨어졌다. 같은 시점 pytest는 30개 전부 통과라 제품보다 검증 쪽을 의심했다.
- **영향**: 스크립트를 연속 2회 실행하면 1회차 64/64, **2회차 2/62**로 확정적으로 재현됐다. 이보다 앞서 첫 E2E 실행에서 46건이 실패하고 재실행하니 3건이 된 일(I-06)이 있었는데, 그때 "격리 상태를 의심하라"로 닫고 원인을 스크립트에서 없애지 않아 다시 터진 것이다.
- **가설**:
  1. 백엔드 구현 결함 — pytest가 전부 통과해서 가능성이 낮다고 봤다.
  2. 이전 실행이 남긴 서버·DB 때문에 상태가 오염됐다.
- **검증**: 연속 실행으로 재현했고, 준비 대기 루프를 읽어 원인을 확정했다.
- **원인**: 준비 대기 루프가 **아무 응답이든 오면 통과**하는 구조였다. 이전 실행의 uvicorn이 포트 8820에 남아 있으면 새 서버 대신 **그 서버**의 응답을 보고 진행했는데, DB 파일은 방금 지운 상태라 그 뒤 검사가 전부 깨졌다.
- **해결**: `scripts/e2e_live_v3.sh` 두 곳을 고쳤다. 커밋 `745683c`.
  - 서버를 띄우기 전에 `lsof`로 **포트가 실제로 빌 때까지 대기**(최대 약 12초, 실패하면 exit 98)
  - 준비 대기 루프에서 매번 `kill -0 $SRV`로 **방금 띄운 서버가 살아 있는지 확인**(죽었으면 exit 97)
- **결과**: 27/64(연속 실행 시 2/62) → 수정 후 **연속 3회 64/64**. 이후 사진 업로드 검사 8건이 추가돼 72건이 됐고, 2026-09-28 재측정에서 연속 3회 **72/0**, 이 문제는 재현되지 않았다.
- **재발 방지**: 스크립트가 매 실행마다 DB를 지우고 포트를 정리한다. CI(`.github/workflows/ci.yml`)의 e2e 잡이 같은 스크립트를 매 push마다 돌린다.
- **배운 점**: 사고를 "재실행하니 되더라"로 닫으면 재발한다. 원인을 재현 가능한 형태로 고친 뒤에 닫는다.

## 4. passlib + bcrypt 5.0에서 기동 실패, 긴 한글 비밀번호는 500 (원본 I-07, BE 트랙)

- **상황**: 2026-09-03, 계약이 `password_hash`를 bcrypt로 지정해 `passlib[bcrypt]`를 설치했더니 첫 해싱에서 죽었다.
  - `AttributeError: module 'bcrypt' has no attribute '__about__'` → 이어서 `ValueError: password cannot be longer than 72 bytes`
- **영향**: 회원가입·로그인이 동작하지 않았다. bcrypt는 72바이트를 넘는 입력을 거부하는데, 한글은 한 글자가 UTF-8로 3바이트라 **한글 24자를 넘는 비밀번호는 500**으로 터질 수 있었다.
- **가설**: passlib과 설치된 bcrypt 버전이 맞지 않는다.
- **검증**: passlib의 마지막 릴리스는 1.7.4(2020년)이고, 백엔드 버전을 알아낼 때 `bcrypt.__about__`을 읽는다. 이 속성은 bcrypt 4.1에서 사라졌고, 당시 설치된 bcrypt는 5.0.0이었다.
- **원인**: 유지보수가 멈춘 passlib과 최신 bcrypt의 비호환, 그리고 bcrypt의 72바이트 입력 제한.
- **해결**: 커밋 `f98d119`.
  - passlib을 빼고 `bcrypt.hashpw` / `bcrypt.checkpw`를 직접 호출(rounds=12). 해시 형식은 `$2b$12$…`로 계약과 같다 — `backend/app/core/security.py`
  - UTF-8 **바이트 길이** 검사를 두 곳에 넣었다. 회원가입 스키마(`backend/app/schemas/auth.py`)는 72바이트 초과를 검증 오류로, `security.py`의 `hash_password`는 `VALIDATION_FAILED`(400)로 막는다. 로그인 검증(`verify_password`)은 72바이트 초과 입력을 예외 없이 `False`로 돌려준다.
- **결과**: 500 → 400 `VALIDATION_FAILED`. 2026-09-28 재측정에서 로그인 p50 약 290ms는 bcrypt rounds=12의 의도된 비용이다.
- **재발 방지**: `backend/requirements.txt`에 passlib을 쓰지 않는 이유를 주석으로 남겼다(`bcrypt>=4.1`).
- **배운 점**: 문자 수와 바이트 수는 다르다. 한국어 서비스에서 길이 제한이 있는 라이브러리는 바이트 기준으로 검사한다.
