## 대본

**[0:00] 슬라이드 1~2 — 오프닝 (30초)**
"안녕하세요, ○조 발표자 장병헌입니다. 저희 조는 '우리가 SK AX AI 도메인팀이고, 고객사에 AX 솔루션을 제안한다'는 전제로 시작했습니다. SK AX가 올해 6월에 내건 비전이 'AI를 도입하는 기업에서 AI가 일하는 기업으로'인데, 저희는 그 문장을 협력사 규모의 반도체 제조사에서 실제로 어떻게 구현하는지 설계했습니다. 서비스 이름은 ReplaceFlow, 부제는 '교체는 2시간, 승인은 일주일'입니다."

**[0:30] 슬라이드 3 — 문제 (60초)**
"이 문제는 저희 팀원의 현업 경험에서 나왔습니다. 팹에서 가스 라인 밸브에 이상이 생기면, 교체 자체는 두 시간이면 끝납니다. 그런데 그 앞에 세 가지가 있습니다. 벤더에 규격이 같은지 확인하고, 유해물질을 다루는 설비라 산업안전보건법·화학물질관리법·고압가스법 중 뭐가 걸리는지 직접 찾고, 그걸 들고 안전관리자에게 메신저로 승인을 받습니다. 이 세 단계가 일주일입니다. 사내 AI에 물어보면 되지 않느냐 — 물어봐도 법령 데이터가 부실해서 엉뚱한 답을 하고, 외부 클라우드 AI는 보안상 못 씁니다. 그래서 결국 사람이 손으로 찾습니다. 저희가 푸는 문제는 정비 기술이 아니라, **흩어진 정보를 사람이 모으는 시간**입니다."

**[1:30] 슬라이드 4~6 — 페르소나·UC·화면 (90초)**
"페르소나는 두 명입니다. 요청하는 설비 엔지니어 김민준, 승인하는 안전관리자 이정호. Use-Case는 7개인데 핵심은 세 개입니다. 엔지니어가 작업요청을 올리고(UC-01), 시스템이 에이전트를 실행하고(UC-02), 안전관리자가 근거를 보고 승인합니다(UC-04). 화면은 두 개로 좁혔습니다. 작업요청 목록과 대시보드, 그리고 상세 화면 — 이 상세 화면이 오늘 데모의 전부입니다. 왼쪽에 에이전트 타임라인, 오른쪽에 승인 패널이 있습니다."

**[3:00] 슬라이드 7 — AI 확장 지점 (60초)**
"AI가 들어갈 자리는 하나가 아니라 넷입니다. 작업요청 하나가 들어오면 오케스트레이터가 네 개 에이전트를 병렬로 돌립니다. A1은 기존 부품과 후보 부품의 규격을 비교해 호환 여부를 판정하고, A2는 설비와 물질로 적용 법령 조문을 찾아 필요한 절차를 목록화하고, A3는 작업허가서와 위험성평가 초안을 쓰고, A4는 벤더 견적요청 초안을 만듭니다. 중요한 건 이 넷이 **정보를 모으고 초안을 쓸 뿐, 승인하지 않는다**는 겁니다. 승인은 안전관리자가 합니다. 산업안전 규제상 승인 주체가 사람이어야 하고, 금융위 AI 가이드라인의 '보조수단성'과 같은 원칙입니다. 3일 범위에서 네 에이전트는 전부 Mock이고, 저희 산출물은 오케스트레이션 구조와 상태머신, 그리고 JSON 계약입니다."

**[4:00] 슬라이드 8 — 프롬프트·JSON (60초)**
"A2 법령 에이전트 프롬프트만 보여드리면, 핵심 규칙은 세 줄입니다. 제공된 법령 인덱스에서만 인용할 것, 절차를 작업 전·중·후로 나누고 근거 조문을 붙일 것, 근거를 못 찾으면 UNKNOWN으로 두고 안전관리자에게 넘길 것. 출력은 이 JSON입니다. steps 배열에 에이전트 넷의 상태와 결과가 들어가고, LEGAL 결과에는 조문 인용과 required_procedures가, 승인에는 체크리스트 네 항목이 들어갑니다. 이 JSON은 JSON Schema로 고정했고, 샘플이 스키마를 통과하는 것과 잘못된 값이 거부되는 것까지 검증했습니다."

**[5:00] 슬라이드 9~10 — 아키텍처·4원칙 (120초)**
"전체 구조입니다. Vue 프론트, FastAPI 백엔드, PostgreSQL. 백엔드 안에 오케스트레이터와 네 개 AgentService 인터페이스가 있고, 지금은 Mock 구현체, 나중에 LLM 구현체로 갈아끼웁니다. AI-Ready 네 원칙을 어떻게 지켰는지 말씀드리면 — Interface First: 프론트는 `GET /agent-runs/{id}`의 JSON만 압니다. Mock을 LLM으로 바꿔도 화면 수정이 없습니다. Structured Data: `agent_runs.steps_json`에 결과를 넣되, 검색이 필요한 법령 결과는 `legal_findings` 테이블로 정규화했습니다. Asynchronous: 에이전트 실행은 `POST` 202로 받고 폴링합니다. Security & Config Isolation: 이게 이 서비스의 존재 이유와 직결되는데, `ai_configs.provider`가 `LOCAL_LLM`이고 `egress_allowed`가 `false`가 기본입니다. 외부로 나가는 설정을 켜려고 하면 409로 막힙니다. 법령은 법제처 Open API에서 사내로 미리 적재합니다 — 사내 AI가 법령을 모른다는 문제를 데이터로 푸는 겁니다."

**[7:00] 슬라이드 11 — ERD (60초)**
"테이블은 14개입니다. 설계 원칙 하나만 말씀드리면 **사실 / AI 산출 / 사람의 결정** 세 층을 분리했습니다. `work_requests`가 사실, `agent_runs`·`legal_findings`·`documents`가 AI 산출, `approvals`가 사람의 결정입니다. N:M은 두 곳 — 설비와 부품은 `equipment_parts`, 부품 호환은 `part_compatibility`. 그리고 승인 게이트를 DB CHECK 제약으로도 걸어서 체크리스트 네 개가 다 true가 아니면 APPROVE 행이 아예 안 들어갑니다. 실제 PostgreSQL 16에서 DDL과 시드를 실행해 확인했습니다."

**[8:00] 슬라이드 12 — API (60초)**
"엔드포인트 15개, OpenAPI 3.0으로 작성해 Redocly 린트 0 에러입니다. 설계 판단 두 가지 — 에이전트 실행은 오래 걸리니 `202 Accepted`로 받고 `run_id`를 돌려준 뒤 폴링하게 했습니다. 409와 422는 '내가 보낸 값을 바꾸면 되는가'로 구분했습니다. 서류 누락은 값을 채우면 되니 422, 체크리스트 미완료 상태에서 승인은 상태를 바꿔야 하니 409입니다. Mock은 폴링할 때마다 step이 하나씩 완료되도록 만들어서, 데모에서 타임라인이 살아 움직입니다."

**[9:00] 슬라이드 13 — 스캐폴딩 (30초)**
"프로젝트 구조입니다. 프론트는 Mock 모드 토글이 있어 백엔드 없이도 돌고, 백엔드는 pytest 8개가 전부 통과합니다. GitHub는 역할별 feature 브랜치로 각자 커밋이 남게 했습니다."

**[9:30] 슬라이드 14 — 라이브 데모 (90초)** → 아래 시나리오

**[11:00] 슬라이드 15 — 회고·확장 (90초)**
"한계는 분명합니다. 에이전트 넷이 전부 Mock이고, 법령 인덱스는 조문 여섯 개, 벤더·ERP 연동은 없습니다. 확장은 세 단계로 — 1단계 법제처 API 전량 적재와 사내 GPU LLM으로 A2를 실제 RAG로, 2단계 ERP·벤더 포털 연동, 3단계 모니터링 알람에서 작업요청 자동 생성. 확산은 이 구조 그대로 '법정 승인이 병목인' 모든 설비 산업 — 조선, 에너지, 화학 — 으로 갈 수 있고, SK AX AXgenticWire 위의 도메인 에이전트 팩으로 포지셔닝합니다. 역할별 회고는 (각자 한 줄)."

**[12:30] 슬라이드 16 — 마무리 (30초)**
"정리하면, 일주일을 하루로 줄이되 판단은 사람이, 수집은 에이전트가 합니다. AI가 일하는 기업이란 AI가 결재하는 기업이 아니라, 사람이 결재만 하면 되는 기업이라고 생각합니다. 질문 받겠습니다."

2. "AI 결과를 사람이 뒤집었을 때 그 기록은 어디에 남고, 다음 응답에 어떻게 반영되나요?" (Human-in-the-loop·데이터 축적)
3. "외부 API를 못 쓰는 고객사에 납품한다면 어느 설정을 바꾸면 되나요?" (Security & Config Isolation)
