# 기록 최신화 지침 — 팀원 전원 적용

> **이 지침은 상시 유효하다.** 별도 지시가 없어도 아래 규칙대로 기록을 갱신한다.
> 목적은 문서를 많이 쓰는 게 아니라, **나중에 서버를 띄워 확인할 때 "왜 이렇게 됐는지"를 5분 안에 알 수 있게** 하는 것이다.

## 0. 한 줄 원칙

**코드가 답할 수 있는 것은 적지 않는다. 코드가 답하지 못하는 것만 적는다.**
파일 목록·함수 시그니처는 코드를 보면 된다. 기록해야 하는 건 **의사결정·번복·실측 증거·사고**다.

## 2. 증거 규칙 (이게 제일 중요하다)

1. **숫자는 실측만.** `pytest -q` 를 실제로 돌린 출력을 저장하고, 그 숫자만 인용한다. "대략 30개쯤" 은 금지
2. **원본 로그를 남긴다.** 요약본만 남기면 나중에 검증이 불가능하다. 파일명에 타임스탬프를 넣는다 (`pytest_20260903_1527.log`)
3. **무효가 된 수치는 지우지 말고 무효라고 표시한다.** v1.0 의 `pytest 8/8` 은 틀린 게 아니라 **대상이 바뀐 것**이다. 그 사실 자체가 기록이다
4. **검증하지 못한 것은 "미검증"이라고 쓴다.** 예: "로컬에 PostgreSQL 이 없어 Supabase 실행은 미검증". 억지로 통과 표시하는 것보다 100배 낫다
5. **캡처는 실연동 상태로.** Mock 화면과 실 API 화면을 구분해 파일명에 표시한다

## 4. 금지 사항

- ❌ 돌려보지 않은 명령의 결과를 적는 것
- ❌ "확인함", "정상 동작", "충분히" 같은 **판정 불가능한 표현** — 무엇을 어떻게 확인했는지 쓴다
- ❌ 실패를 성공으로 표시하거나 조용히 지우는 것
- ❌ 이전 결정 행을 **덮어쓰는 것** (번복은 추가로 기록)
- ❌ 다른 담당의 파일을 고치는 것 (필요하면 요청한다)
- ❌ **파일 삭제에 와일드카드를 쓰는 것** — `rm backend/*.db` 같은 명령. 파일명을 명시한다. 각자 DB 는 고유 이름을 쓰고(`e2e_v3.db`·`be_v3_dev.db`), 공유 개발 DB `replaceflow.db` 는 아무도 지우지 않는다 (사고 I-08)

## 6. 노션 동기화

팀 협업 페이지에 같은 내용을 요약해 둔다. **로컬이 원본, 노션이 사본**이다.
노션에는 링크와 요약만 두고 원본 로그는 저장소에 남긴다 — 노션에 대용량 로그를 붙이면 아무도 안 읽는다.

동기화 대상: 상태 한 줄 · 실측 표 · 결정 로그 · 사고 로그 · 남은 일. **하루 1회 이상.**
