# 의사결정 로그

> 형식: **결정 / 근거 / 대안과 기각 사유 / 되돌릴 수 있는가**.
> 결정이 바뀌면 지우지 말고 **아래에 번복 행을 추가**한다. 왜 바뀌었는지가 회고의 재료다.

## D-01 · v1.0 → v2.0 전면 개정 (09-03 오후)
- **결정**: 화면 2개 → 9개, 인증 추가, 에이전트 4종 → 3종, 체크리스트 blocking 폐지
- **근거**: `WRA 화면정의서 v2.0`(09-03 10:23). 역할이 섞인 단일 화면으로는 "안전관리자는 승인만 하면 된다"는 핵심 주장을 화면으로 증명할 수 없었다
- **대안**: (A) v1.0 유지하고 v2.0 을 로드맵으로만 제시 (B) 전면 v2.0 (C) 선별 반영
- **기각**: A 는 리스크가 가장 낮지만 설계 의도를 화면으로 못 보여준다. C 는 제출본과 코드가 어긋난다
- **결정자**: 팀장 · **되돌리기**: 어려움(제출 PDF 재생성 필요)

## D-02 · 계약 v2.0 폐기, v3.0 채택 (09-03 15:00) ← **번복**
- **결정**: 오케스트레이터가 추론해 만든 계약 v2.0 을 폐기하고, 팀 노션 원본 2종을 그대로 옮긴 v3.0 으로 교체
- **근거**: 팀에 이미 「API 명세서 v1.0 (REQ-F-0001)」과 「FixGuide 데이터 모델 정의서 v3.0」이 있었다. v2.0 은 화면정의서만 보고 나머지를 추론한 것이라 PK 체계·상태값·에러포맷·테이블 수가 전부 달랐다
- **영향**: 5개 트랙 약 40분 재작업. 상세는 `incident_log.md` I-01
- **되돌리기**: 불가(원본이 권위 문서)

## D-03 · PK 를 UUID v4 + 자연키 분리로
- **결정**: 전 테이블 UUID v4 대리키. 업무 번호는 `work_requests.request_no varchar(20) UNIQUE` 로 분리
- **근거**: 팀 ERD 원칙 1 — "번호·코드 체계가 바뀌어도 FK 무결성 유지, 조인은 대리키로"
- **기각한 대안**: `WR-`/`RUN-` 접두어 문자열 PK(v1.0·v2.0 방식). 번호 체계 변경이 FK 전파로 번진다

## D-04 · `PENDING_APPROVAL` 이 아니라 `PENDING`
- **결정**: 상태 enum 과 대시보드 KPI 필드 모두 `pending`
- **근거**: 팀 명세서의 상태 enum 이 `PENDING`. 화면정의서의 "승인 대기"는 라벨이고 코드값이 아니다
- **발견 경위**: 라이브 E2E 에서 BE(`pending`) ↔ OpenAPI·Postman(`pendingApproval`) 불일치 검출. **BE·FE 가 이미 `pending` 으로 일치**해서 동작하는 코드 쪽을 정답으로 확정하고 문서 3종을 수정
- **되돌리기**: 쉬움(문자열 치환)

## D-05 · 에이전트 A4(벤더)를 Phase 2 로
- **결정**: 구현 3종(A1 규격·호환 / A2 법령 / A3 안전서류)만
- **근거**: 벤더 견적은 외부 시스템 연동이 필요해 **온프레미스 전제(`egress_allowed=false`)와 충돌**한다. 3일 범위에서 Mock 으로 흉내 내면 나머지 3개의 근거 품질까지 의심받는다
- **발표 프레이밍**: "더 만들었다"가 아니라 "무엇을 왜 뺐는지 판단했다"

## D-06 · 체크리스트 blocking 폐지, 자가승인 차단은 유지
- **결정**: 승인 시 체크리스트 4항목 강제(409)를 없앤다. **단, 요청자 자가승인 차단(403)과 SAFETY_MANAGER 역할 검증은 유지**
- **근거**: 화면정의서 v2.0 변경 ⑥. 체크리스트를 없애도 승인 권한 자체는 사람에게 남으므로 Human-in-the-loop 은 유지된다
- **주의**: v1.0 데모의 클라이맥스가 이 체크리스트 409 였다. 데모 시나리오를 "결과 편집 → 제출 → 승인/거절+사유"로 교체함

## D-07 · N:M 관계를 이번 범위에서 제외
- **결정**: 법령 마스터·설비 마스터·호환표와 그에 딸린 N:M 3종을 Phase 2 로
- **근거**: 팀 ERD 명시. A1 부품 마스터 연동과 한 몸이라 지금 넣으면 Mock 단계에서 아무도 참조하지 않는 빈 테이블이 된다
- **⚠️ 리스크**: 루브릭 30점 항목이 "테이블 관계(1:N, **N:M**) 및 정규화 타당성"을 요구한다
- **완화**: `erd.md` 에 1:N 8개 표 + "왜 N:M 이 없는가" 절 + **Phase 2 예비 N:M 설계(DBML 스니펫 + `erd_phase2.svg` 다이어그램)** 를 넣었다. "모른다"가 아니라 "설계는 끝냈고 범위에서 뺐다"로 방어
- **미결**: 실제로 하나 넣을지는 팀장 판단 대기

## D-08 · GitHub 커밋을 팀장 계정으로 통합, 담당은 본문에 명시
- **결정**: 커밋은 `jang961111-hash` 단일 명의. **커밋 본문에 담당 역할·이름을 남긴다**
- **근거**: 팀원 명의로 커밋을 만드는 것은 저작자 위조다. 하지 않는다
- **⚠️ 리스크**: 루브릭 "GitHub 관리 및 R&R 분담" 항목. `git shortlog -sn` 이 1인으로 나온다
- **완화**: `develop` + `feature/*` 브랜치·PR 을 실제로 만들어 브랜치 전략은 적용된 상태로. 발표·`qa_bank.md` 에서 **"각자 계정으로 커밋했다"고 말하지 않는다** — 사실대로 "산출물은 5인 분담, 통합 커밋은 단일화, 담당은 커밋 본문에 명시"
