## I-07 · `passlib` 이 bcrypt 5.0 에서 아예 기동하지 않음
- **무슨 일**: 계약 §5 가 `password_hash` 를 bcrypt 로 지정해 `passlib[bcrypt]` 를 설치했더니 첫 해싱에서 죽었다
  - `AttributeError: module 'bcrypt' has no attribute '__about__'` → 이어서 `ValueError: password cannot be longer than 72 bytes`
- **원인**: `passlib` 마지막 릴리스가 **1.7.4(2020년)** 인데 백엔드 버전 탐지에 `bcrypt.__about__` 을 쓴다. `bcrypt` 4.1 에서 그 속성이 사라졌고 지금 설치되는 건 5.0.0 이다
- **조치**: `passlib` 을 걷어내고 `bcrypt` 를 직접 호출(`bcrypt.hashpw/checkpw`, rounds=12). 해시 포맷은 `$2b$12$…` 로 계약과 동일
- **밟기 쉬운 지점**: bcrypt 는 **72바이트 초과 입력을 예외로 거절**한다. 한글은 1자 3바이트라 **24자를 넘는 한글 비밀번호가 500 으로 터진다.** `core/security.py` 와 회원가입 스키마 양쪽에 바이트 길이 검사를 넣어 400 `VALIDATION_FAILED` 로 처리했다
- **재발 방지**: `requirements.txt` 에 사유를 주석으로 남김. 다른 프로젝트에서 `passlib` 을 쓸 거면 `bcrypt<4.1` 로 묶든가 직접 호출한다

## I-08 · SQLite 에서 시각의 타임존이 사라져 계약 위반이 될 뻔함
- **무슨 일**: 계약 §1 이 `2026-09-03T10:22:00+09:00` 처럼 **KST 오프셋 포함**을 요구하는데, `DateTime(timezone=True)` 로 선언해도 **SQLite 는 tzinfo 를 저장하지 않아** 읽을 때 naive 로 돌아온다. 그대로 직렬화하면 오프셋 없는 문자열이 나간다
- **어떻게 알았나**: 응답을 눈으로 보다가 `createdAt` 에 `+09:00` 이 없는 걸 발견
- **조치**: `app/schemas/base.py` 의 `KstDatetime`(PlainSerializer)이 **naive 는 UTC 로 간주해 KST 로 변환**한 뒤 ISO 문자열로 낸다. 전 응답 시각 필드가 이 타입을 쓴다
- **주의**: PostgreSQL 로 옮기면 tz 가 보존되므로 이 변환은 무해하게 통과한다. **DB 를 바꿔도 응답이 바뀌지 않는지**는 PG 에서 한 번 더 봐야 한다
- **회귀 방지**: `test_auth.py`·`test_flow.py` 가 `createdAt`·`submittedAt`·`decidedAt` 의 `+09:00` 접미사를 검사한다

## I-09 · 로컬 SQLite 와 배포 PostgreSQL 이 **다르게 도는** 구간이 있다 (일부 미검증)
- **무슨 일**: 계약 §5 는 UUID PK · `jsonb` · **PostgreSQL enum** 을 요구한다. SQLite 에는 셋 다 없다
- **조치**: `app/db/types.py` 에서 `.with_variant()` 로 갈라 둠 — PG 는 `uuid`/`jsonb`/네이티브 enum, SQLite 는 `char(36)`/`JSON`/`VARCHAR + CHECK`
- **밟기 쉬운 지점**: **제약의 강도가 다르다.** SQLite 쪽 CHECK 는 PG enum 만큼 촘촘하지 않아, 잘못된 상태 문자열이 로컬에서는 통과하고 Supabase 에서 터질 수 있다. 애플리케이션 레벨(Pydantic enum)이 1차 방어선인 이유다
- **미검증**: 로컬에 PostgreSQL 이 없어 **Supabase 실제 기동은 확인하지 못했다.** `DATABASE_URL` 만 바꾸면 되도록 코드는 갈라 뒀지만, DDL 생성·enum 타입 충돌은 실행해 봐야 안다

## I-10 · `request_no` 채번의 동시성 방어가 DB 마다 다르다 (부하 미검증)
- **무슨 일**: `WR-YYYYMMDD-NNN` 은 "당일 최대 +1" 이라 동시 생성이 겹치면 같은 번호가 나올 수 있다. ERD 문서가 "시퀀스 또는 행 잠금"을 요구했다
- **조치**: `repositories/request_no.py` — PostgreSQL 에서는 당일 행을 `SELECT … FOR UPDATE` 로 잠그고, **SQLite 에는 `FOR UPDATE` 가 없어** UNIQUE 제약 위반을 잡아 최대 5회 재채번한다. 최종 방어선은 `request_no` UNIQUE 인덱스다
- **미검증**: **동시 요청 부하 테스트는 하지 않았다.** 순차 생성이 001·002·003 으로 증가하는 것만 확인했다(`test_request_no_is_unique_and_sequential`)
- **밟기 쉬운 지점**: 이 로직을 고칠 때 UNIQUE 인덱스를 지우면 방어선이 통째로 사라진다

## I-12 · E2E 스크립트의 한 판정이 **값과 무관하게 항상 통과**한다 (미해결, 소유: API Architect)
- **무슨 일**: `scripts/e2e_live_v3.sh:287` 의 대시보드 키 검사가 출력에 `PASS … FAIL:['aiRunning','draft','pending','rejected']` 라는 모순된 줄을 낸다
- **원인**: `python -c "…"` 안의 집합 리터럴 `{'draft','aiRunning','pending','rejected'}` 를 **bash 가 brace expansion 으로 전개**한다. 인자 하나가 4개로 쪼개져 `chk` 가 `$2` 를 **자기 복사본과 비교**하게 되고, 실제 값이 무엇이든 PASS 다
- **증거**: 인자를 찍어보면 `ARGC=6`, `[2]`=`[3]`=`FAIL:[…]`, 기대값 `OK` 는 `[6]` 으로 밀려 있다. 같은 응답 본문에 그 파이썬 스니펫을 **단독 실행하면 `OK`** 가 나온다 → **BE 응답은 정상**
- **조치안(검증됨)**: `{…}` 를 `set([…])` 로 바꾸면 `ARGC=3`, 값 `OK` 로 정상화된다. 스크립트에 이 패턴은 **1곳뿐**이라 나머지 63건 판정은 유효하다
- **상태**: 스크립트가 BE 소유가 아니라 손대지 않았다. 팀장에게 보고함
- **교훈**: I-04 의 반복이다 — **검증 스크립트도 코드다.** 특히 "통과인데 값이 이상한" 줄은 무시하지 말고 인자를 찍어본다

  - 그 DB 에는 시드 외 수동 데이터가 없었다(캡처를 위한 조회만 했고 생성은 안 했다)
- **재발 방지**: DB 정리 시 **와일드카드 금지, 파일명 명시.** 각 담당은 자기 DB 를 고유 이름으로 쓴다 (`e2e_v3.db`, `be_v3_dev.db`, `_probe.db` 등). 공유 개발 DB 는 `argus.db` 하나뿐이고 이건 아무도 지우지 않는다
- **교훈**: 사고 자체보다 **보고 방식이 좋았다.** "지웠다"가 아니라 "지웠고, 영향 범위는 여기까지고, 복구 가능한 것과 아닌 것은 이렇게 갈린다"였다. 이 형식을 팀 표준으로 삼는다

## I-09 · 검증 스크립트가 인자를 잘못 받아 일부 검사가 실제로 비교되지 않았다 (09-03 16:0x, 수정 완료)
- **증상**: E2E 출력 한 줄이 `PASS ... FAIL:['aiRunning', 'draft', ...]` 로, **판정은 PASS 인데 값에 FAIL 문자열**이 찍혔다. API 담당이 "원인 못 찾음, 미해결"로 정직하게 남겨 뒀고 오케스트레이터가 이어받았다
- **처음엔 미관 문제로 보였다.** 실제로는 검증 버그였다
- **원인**: 여러 줄 명령치환을 `chk` 인자로 직접 넘기는 형태
  ```bash
  chk "이름" "$("$PY" -c "
  ...python...
  ")" "OK"
  ```
  파이썬 출력에 **공백이 있으면 단어 분리**가 일어나 `chk` 가 인자 3개가 아니라 **6개**를 받는다(디버그 계측으로 `argc=6` 실측). 그러면 `[ "$2" = "$3" ]` 가 엉뚱한 조각끼리 비교하게 되어 **판정이 무의미해진다**
- **왜 위험한가**: 값에 공백이 생기는 건 주로 **실패 경로**다(예: `FAIL:['a', 'b']`). 즉 **검사가 실패해야 할 때 조용히 통과할 수 있다**. 통과 개수만 보면 알 수 없다
- **범위**: 같은 패턴을 쓰는 검사 **10곳**. 공백 없는 값(`OK`/숫자)만 내는 검사는 실질 영향이 없었으나, 보장은 주장보다 약했다
- **수정**: 명령치환을 **먼저 변수에 대입**하고(`_cv5=$(...)` — 대입 문맥에서는 단어 분리가 없다) `"$_cv5"` 로 넘기도록 10곳 전부 변환
- **검증**: 수정 후 대시보드 검사가 `OK` 로 제대로 판정되고 **72/0 통과**(사진 §14 8건 추가 반영)
- **교훈**: **검증 도구 자체를 검증해야 한다.** "통과 개수"는 검사가 실제로 비교하고 있다는 증거가 아니다. 이상한 출력 한 줄을 미관 문제로 넘겼으면 못 잡았다 — 담당이 "원인 못 찾음"으로 정직하게 남긴 덕분에 추적할 수 있었다

## ⚠️ 기록 정합성 메모 (BE·발표 장병헌, 09-03 · 발표 인용 수치 확인 중 발견)

**기존 항목은 하나도 고치지 않았다**(RECORD_KEEPING §4 — 덮어쓰지 않고 추가로 기록). 아래는 발표에서 이 로그를 근거로 인용하기 전에 정리가 필요한 두 가지다.

1. **ID가 3쌍 중복된다.** `I-07`·`I-08`·`I-09`가 각각 두 번 쓰였다 — 앞쪽 3건은 BE 트랙(passlib / SQLite 타임존 / SQLite↔PG 차이), 뒤쪽 3건은 오케스트레이터(이전 서버 잔존 / 개발 DB 삭제 / 검증 스크립트 인자). **총 항목은 9건이 아니라 15건이다.** 발표에서 "사고 N건"이라고 개수를 말할 거면 재번호가 필요하다.
2. **`I-12`(값과 무관하게 항상 통과, "미해결")는 사실상 해결됐다.** 뒤쪽 `I-09`가 같은 증상의 근본 원인(명령치환 단어 분리로 `chk` 인자 6개 수신)을 찾아 10곳을 고쳤고 이후 72/0이다. **`I-12`를 "미해결"로 둔 채 제출하면 로그가 자기모순이다.** 소유자(API Architect·오케스트레이터) 확인 후 상태 갱신 필요.

**발표 대본에서는** 이 사고를 **"검증 스크립트가 인자를 잘못 받아 실패 경로에서 조용히 통과할 수 있었던 건"** 이라고 **설명으로 부르고, ID를 말하지 않는다.** 재번호가 끝나면 ID를 붙인다.
