## Keep — 잘한 것

- **계약서 하나를 단일 기준으로 둔 것.** `docs/CONTRACT.md`에 상태값·필드명·API·에러 코드를 고정하고 병렬 트랙이 모두 여기에 맞췄다. 계약이 v1.0 → v3.0으로 두 번 바뀌는 동안에도 통합이 가능했던 이유다. 프런트는 상수를 한 파일에 모아 둬서 계약 변경 피해가 가장 작았다.
- **단위 테스트에서 멈추지 않고 실서버 E2E까지 만든 것.** pytest 30개(TestClient)와 별도로, 실제 uvicorn을 띄워 72건을 검사하는 스크립트를 만들고 CI에 넣었다. 이 E2E가 문서와 구현의 필드명 불일치(대시보드 `pending` vs `pendingApproval`)를 잡았다.
- **검증 도구 자체를 의심한 것.** "PASS인데 값이 FAIL"인 한 줄을 표시 문제로 넘기지 않고 인자를 찍어 봐서, 실패 경로에서 조용히 통과하는 검사 10곳을 찾았다([트러블슈팅 2](TROUBLESHOOTING.md)).
- **"미검증"을 미검증이라고 적은 것.** 당시 PostgreSQL 실기동과 채번 부하는 확인하지 못했고, 사고 로그에 그대로 남겼다. 덕분에 사후 재측정에서 무엇부터 확인할지 바로 정할 수 있었다.

## Problem — 아쉬운 것 (구체적 결과와 함께)

- **AI가 전부 Mock이다.** main의 에이전트 3종은 고정 JSON을 돌려준다. `llm_agents.py`는 `NotImplementedError` 스텁이고 커버리지 0%다. "AI 에이전트 워크플로"라고 소개하기에는 AI 부분의 실체가 없다. A2 법령 에이전트의 Claude 구현은 `feat/a2-legal-llm` 브랜치에서 진행 중이고 실측 수치는 아직 없다.
- **커밋이 하루에 몰려 있다.** main 43커밋이 모두 2026-09-03 14:14~22:06 사이다. 에이전트 트랙을 병렬로 돌린 1일 스프린트였기 때문이지만, 커밋 이력만 보면 작업 흐름을 따라가기 어렵다. 같은 초에 여러 커밋과 merge가 찍힌 구간도 있다.
- **당시 PR이 0건이었다.** 브랜치(`feature/*` 10개, `develop`)는 만들었지만 전부 로컬에서 merge했고 리뷰 기록이 없다. PR은 사후 보완부터 쌓기 시작했다(PR #1).
- **문서 속 담당자 표기가 오해를 부를 수 있었다.** `docs/` 곳곳에 "은태현 담당", "신서현 담당"처럼 팀원 이름이 붙어 있는데, 이는 팀 R&R을 에이전트 트랙에 매핑한 표기다. README에 이 사실을 적기 전까지는 실제 팀원이 이 레포를 작성한 것처럼 읽혔다.
- **README가 코드보다 뒤처져 있었다.** 계약 v1.0 시절 README가 남아 "에이전트 4개 병렬", "ERD 14개 테이블", "체크리스트 미체크 시 409"를 주장했다. 실제 코드는 에이전트 3개 순차, 테이블 7개, 409 규칙 폐지다. 2026-09-28에 전면 재작성했다.
- **계약을 원본 확인 전에 확정했다.** 팀 노션의 원본 명세를 다 열어 보기 전에 링크 하나만 보고 계약 v2.0을 만들었다가, 원본(테이블 7개·UUID PK)과 달라서 5개 트랙이 약 40분 재작업했다(당시 기록 `incident_log.md` I-01).
- **SQLite 동시성 한계가 미해결이다.** 2026-09-28 재측정에서 SQLite 모드는 동시 요청 **80 이상**이면 약 30초 멈춘 뒤 500을 냈다(동시성 70까지는 200건 전부 성공). 같은 조건의 PostgreSQL은 동시성 100에서도 전부 성공했다. 서버 로그에 `QueuePool limit of size 5 overflow 10 reached`가 남지만, 커넥션 풀·동기 의존성·SQLite 파일 잠금 중 무엇이 원인인지는 아직 확인하지 못했다.
- **마이그레이션 도구가 없다.** `create_all()`은 기존 테이블을 ALTER하지 않고, 시드는 `users`에 한 행이라도 있으면 건너뛴다. 스키마를 바꾸면 개발 DB 파일을 지우고 다시 띄우는 것으로 회피했다.
