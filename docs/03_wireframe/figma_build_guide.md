## 5. 우선순위 3등급 (전제 갱신 — 9화면 전부 실물·캡처 확보됨)

**바뀐 전제**: 이전 지시서는 "FE 2뷰만 구현됨 → Figma가 나머지 7화면의 설계 의도를 대신 보여준다"를 전제했다. 지금은 **9화면 전부 실제 API로 구현되고 8화면이 캡처로 확보**됐다(`WRA_C_01` 회원가입만 캡처 없음 — 10절 참조). 따라서 Figma/Stitch의 역할은 "없는 화면을 그리는 것"이 아니라 **"이미 동작하는 화면 중 설계 의도·상태 변형(로딩/에러/빈 상태 등)이 스크린샷 한 장으로는 안 보이는 화면을 정리해 보여주는 것"**이다. 이 기준으로도 **3등급 배치 자체는 그대로 유효하다** — 다만 근거가 "화면이 없어서 필수"에서 "실제 화면을 봐도 여전히 UI 복잡도·차별점이 가장 큰 화면이라 필수"로 바뀐다.

| 등급 | 화면 | 근거(갱신) |
|---|---|---|

**결론**: UC-01·02·03·06은 화면정의서 v2.0에 맞춰 **본문 개정**이 필요하고, UC-04는 **개정이 필수**(현재 문서가 실제 화면과 반대되는 로직을 서술 중이라 그대로 두면 명백한 오류로 지적받는다). UC-05·07은 기존과 동일하게 "PoC 범위 의도적 제외"로 커버 페이지에 명시하는 방어가 유효하다.

## 9. Peer Review(UX 40%) 관점 약점 3개 + 최소 수정안 (v3.0 실연동 캡처 기준)

> v2.0 판정에서 지적했던 "로그인/회원가입이 실제 구현(역할 토글)과 다른 세계관을 전제한다"는 약점은 **이제 해소됐다** — `WRA_C_00`이 실제로 이메일/비밀번호 로그인 화면으로 구현·캡처됐다(10절). 아래 3개는 v3.0 실물을 보고 다시 뽑았다.

1. **평균 승인 소요시간 KPI(As-Is 168h → 84% 단축) 삭제가 실물로 확정됐다.** `WRA_E_01`, `WRA_S_01` 캡처 모두 KPI가 4종뿐이고 승인 소요시간 지표가 없다. 이 지표가 "서비스가 해결하는 문제(승인 지연)"의 가장 강한 정량 근거였는데, 실제 화면 어디에도 없다는 게 캡처로 확정됐다.
   → 최소 수정: 화면은 그대로 두고(팀 결정 존중), 발표 슬라이드 또는 Figma/Stitch 커버 페이지에 이 지표를 별도로 유지한다.

2. **UC-04 문서와 실제 `S_02` 화면의 승인 로직이 서로 다르다는 것이 캡처로 확정됐다.** `usecase_spec.md`는 "체크리스트 4항목 모두 확인해야 승인 가능(서버가 409로 강제)"을 안전장치로 명시하는데, 실제 화면은 "체크리스트 게이트 없이 승인 / 거절+사유로 처리합니다"라는 문구를 화면 자체에 띄우고 있다(`WRA_S_01`, `WRA_S_02` 캡처). 이제는 가능성이 아니라 **이미 배포·데모 예정인 동작**이므로 문서 불일치를 방치하면 발표 중 직접 지적당할 위험이 크다.
   → 최소 수정: `usecase_spec.md` UC-04를 화면 그대로(체크리스트 게이트 삭제, 승인/거절 2種)로 개정한다. 오늘 밤 확정 필수.

3. **상태 칩 색상이 유사색이라 목록에서 빠르게 구분되지 않는다(신규, 캡처로 발견).** `WRA_E_01`·`WRA_E_05` 캡처를 보면 "결과 확인 대기"(`--primary` 계열, 연한 파랑 배경 `#e8efff`)와 "AI 검증중"(`--info` 계열, 연한 하늘 배경 `#e0f4f8`)이 육안으로 상당히 비슷하다 — 두 배경색의 HEX 차이가 크지 않고(2절 토큰 표), "AI 검증중"에만 작은 점 아이콘이 붙어 구분되는 정도다. 목록 화면(엔지니어 메인·내 요청·요청 관리)은 상태를 빠르게 스캔하는 게 핵심 태스크인데, 색만으로 구분이 어려우면 "UI 와이어프레임이 직관적인가" 채점에서 감점 요인이 될 수 있다.
   → 최소 수정: `REVIEW`류 상태 색을 primary(파랑)에서 채도·색상환이 더 벌어진 계열(예: 보라)로 바꾸거나, 점 아이콘을 모든 상태 칩에 일관 적용해 색이 아닌 형태로도 구분되게 한다. 코드 수정 범위이므로 이 문서에는 제안만 남기고 실제 변경은 팀 확인 후 진행.
